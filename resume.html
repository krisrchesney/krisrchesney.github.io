Personal Projects

Payments Ops AnalystDatabricks · PySpark · Claude Code · Evaluation

A personal project on simulated card payment data, not production or employer work. I used Claude Code to assist in development: I set the requirements and product decisions, guided the build, reviewed and approved the code, and ran the deployments and tests. It includes a formal test of an AI agent that investigates payment incidents. The pass/fail rules were written before any run, with 4 questions run 3 times each, and every answer was graded against an answer key and rechecked with SQL. The results are published with the failures: 8 of 12 runs passed. When a question pointed at the problem, the agent found the true cause and the right document in 9 of 9 runs, but 2 of those answers had a wrong figure. With no hint, 1 of 3 runs found all three planted incidents, which is why automatic detection is next. The data, documents, and questions are mine and the sample is small, so 8 of 12 is not an accuracy rate. Monitoring and alerts are planned, not built.

Agent Team EvalsPython · Claude Code · Evaluation

Asks whether a team of Claude agents (a planner, builders, and a reviewer) writes better code than a single agent. It runs the same coding tasks through three setups and grades each against hidden tests, measuring pass rate, tokens, and time. The first study was too small to settle it: in a 45-run pilot, one agent passed 14 of 15 runs and each team passed 15 of 15, while the teams used 1.6 to 2.8 times the tokens. A second study used 11 tasks a single agent can fail, with five runs per task for each setup. One agent passed 15 of 55 runs and a builder plus reviewer passed 11 of 55 at roughly 1.5 times the tokens, a gap too small to separate from chance. A further 132 runs on Haiku and Opus found no model or mixed team that beat one Sonnet agent. Parallel work and much larger codebases are still untested.

ShowMe CouncilPython · Claude agents · Data pipeline

A nightly pipeline of Claude agents that turns Kansas City Council records into plain-language, fact-checked summaries. An extractor agent pulls out votes, spending, and dates with verbatim quotes. A summarizer writes only from those facts. A fact-checker agent and code checks then verify the quotes, the numbers, and the city's own vote record. KEV WatchPython · Machine learning · Security analytics

Ranks newly published vulnerabilities by how likely they are to land in CISA's Known Exploited Vulnerabilities catalog within 90 days. It scores each CVE from what the publisher released, updates daily, and checks its ranking against EPSS. A gradient boosting model reached a ROC AUC of 0.87 on a held-out test set, and the write-up is plain about its limits: it was not better than EPSS at the very top of the list, and the test set had only 37 positive CVEs.

GitHub Issues TriagePython · FastAPI · Ticket triage · Drift monitoring

Predicts, at the moment a GitHub issue is opened, whether maintainers will close it within 14 days. It is trained on issues from large Google-backed open-source repositories, served through a validated FastAPI endpoint, and monitored for drift. Issue queues are ticket queues, so it answers the question a support team asks at intake: which new tickets will stall?

BoxwatchWeb app · Python · BoardGameGeek data

Plans where your board games go on the shelf. Park Wait ForecastPython · FastAPI · Forecasting · Drift monitoring

Forecasts whether an open theme-park ride's posted wait will be at least 45 minutes one hour from now. It is trained on ride wait snapshots collected every 10 minutes, served through a validated FastAPI endpoint, and monitored for data and performance drift. Tests guard against future information leaking into features, and the build prints a "wait stays the same" baseline that the model has to beat. The pipeline and tests are complete, and real-data results are not published yet.
